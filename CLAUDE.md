# WP Steps — notes for the next agent

Read this first, then `README.md` and `readme.txt`.

## What it is

The user's fourth plugin (after WP Swiper, WP Banner, WP Maps Embed), started 2026-11-16 from four reference pictures of step infographics. Steps are written once and drawn by a **design**; the user will keep adding designs ("these four are only a few of the possible ones"), so a new design must stay a self-contained module (see README "Adding a design"). Everything must be responsive.

Plugin author: **Relevant AS** (https://relevant.no/), the user's rule (2026-11-25). Commits: author **Andrii Boiko <andrusi4ka1985@gmail.com>** only (set in this repo's git config), never a Claude co-author line. Folder `wp-content/plugins/wp-steps`, a git working copy of https://github.com/Andrusi4ka/WP-Steps (public), branch `main`; first release **v1.0.0** (2026-11-25).

## Where things are

**Large files are split into parts (2026-11-25, user's request: smaller files, easy to read).** Edit the parts, never the joined files:
- `assets/js/admin/01-start.js … 13-preview-save.js` → `assets/js/admin.js`; `assets/css/admin/*.css` → `assets/css/admin.css`; `assets/css/frontend/*.css` → `assets/css/frontend.css`. `tools/build.cjs` joins them in name order, nothing between (`npm run build`; `npm test` builds first; `node tools/build.cjs --check` exits 1 if a joined file is stale). WordPress and the tests load only the joined files; the parts and tools/ are export-ignore. admin.js is still one function: 01 opens it, 13 closes it, so the middle parts share its variables (an editor may show 01 / 13 as unfinished code: that is expected). A new part: a name between two others (e.g. `08b-…`).

## Design notes (the tricky parts)

- Zigzag: rows of five columns (side | point | middle | point | side), rows equal height (`grid-auto-rows: 1fr`) so the curve between markers is exactly row + gap tall; the curve is two quarter-ellipse borders.
- Wave: the steps share three rows through `subgrid`; a column must NOT be a size container (containment ends the subgrid), its width is `100cqw / --wpst-n`. Folded: rows equal height so the line between rings is computable.
- Timeline folded: line on the left, side text above the card.

## Roles, updates, What's new, release (2026-11-25, user's requests before the first push)

- **WP Steps → Settings** (`WP_Steps_Access`, includes/class-wp-steps-access.php, as WP Swiper's `WP_Swiper_Roles` / WP Banner's `WPBN_Access`): a submenu after Add new, `manage_options` only, a "Settings" link under Plugins too; a table of the site's roles × Edit steps / Add new / Delete / WPBakery element (the last three only with Edit: `sanitize()` and assets/js/roles.js), option `wp_steps_roles`. The plugin's own capabilities (`EDIT` / `CREATE` / `DELETE` / `WPBAKERY`) are given at run time by `user_has_cap` (`grant()`), never written into roles; the post type maps its capabilities to them (wp-steps.php) and every check uses them (`WP_Steps_Access::can()`: the meta's auth_callback, the WPBakery element and its list). Unset, only Administrators have WP Steps (before, anyone with edit_posts had it).
- **Updates from GitHub** (`wp_steps_updates()`, Plugin Update Checker 5.7 in vendor/, copied from WP Banner): a release's `wp-steps.zip` shows under Plugins as any update, with View details and Check for updates. **Never for a git working copy** (`wp_steps_is_working_copy()`, filter `wp_steps_is_working_copy`): an update replaces the folder and would wipe `.git` (it happened to WP Swiper on 2026-11-04). So this work site never offers it; check updates on another site.
- **What's new** (`WP_Steps_Whats_New`, assets/js/whats-new.js + css, as WP Banner's): after an update, once per user who may edit the steps, a window on the plugin's screens (a notice with a link on the Dashboard) with the readme's Changelog items of the versions since the one they saw (options `wp_steps_version`, `wp_steps_updated_from`, user meta `wp_steps_seen_version`). Not after a first install (no sets). So **every release needs its Changelog section in readme.txt** (a PHP test checks the current version has one).
- **A step's window asks before closing with changes** (Cancel, ×, Esc; not Apply): `closeStep()` compares the step with `stepBefore`, `confirm()`; No keeps it open with the changes. Leaving the page with unsaved changes keeps the browser's own question (`beforeunload`).
- **Release** (only at the user's word): one number in wp-steps.php (header `Version:` and `WP_STEPS_VERSION`) and readme.txt (`Stable tag:` + a `= X.Y.Z =` Changelog section), `npm test`, commit, push `main`, then tag `vX.Y.Z` and push it: .github/workflows/release.yml runs tests.yml (PHP 7.4 / 8.3 syntax, `node tools/build.cjs --check`, JS syntax, tests/settings.php), checks the three numbers match, builds wp-steps.zip by `git archive` (export-ignore: dev files and the parts of the built files) with the JS / CSS minified in the copy, and publishes the release. Actions pinned by SHA (as WP Banner's). GitHub Actions status: api.github.com/repos/Andrusi4ka/WP-Steps/actions/runs.
- uninstall.php also deletes those options, the user meta and the update checker's `external_updates-wp-steps`.
